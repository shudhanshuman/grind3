3How interviews have changed in the AI era (applies to every folder)
  1. The OA is still the gate, but more of it is proctored. Codeforces-style OAs (HackerRank, HackerEarth, Codility) now have webcam and screen monitoring and plagiarism/AI-similarity checks. Many firms (especially quant/HFT in India: Graviton, Quadeye, Tower, Optiver, APT, NK Securities, AlphaGrep, etc.) moved more rounds back to live or in-person interviews. Raw DSA ability matters more now, not less.
  2. "Walk me through your project" got harder. Interviewers assume any repo could be AI-generated, so they probe: why this data structure, what you measured, what broke, what you'd change, what the alternative was. Every theory.md has a "defend your design" list. Make sure you can answer it without notes.
  3. Code-reading and debugging rounds. You're given AI-written or buggy code and asked to find the bug, the performance problem or the race. Projects where you hit the bugs (perft mismatches, CDC glitches, use-after-free in a pool allocator) are your training data.
  4. Using AI is allowed in some rounds. Some companies now run "AI-assisted" rounds where you can use Copilot/Claude, and they grade how well you specify, verify and test. The skill is: write the spec and tests yourself, let AI draft, verify with a golden model. That is exactly the workflow in these projects (C++ model ↔ RTL, python-chess ↔ your perft, FAISS ↔ your recall).
  5. Numbers beat adjectives. "p99 add-order latency 85 ns", "recall@10 = 0.95 at 12k QPS on SIFT1M", "perft(6) correct, 1.2 M nps", "parses one ITCH message per cycle at 250 MHz". Every theory.md ends with the metrics you should report.

Limit Order Book (LOB) + Matching Engine

Goal: a C++ limit order book that (a) matches orders like an exchange and (b) rebuilds the real NASDAQ book from an ITCH 5.0 file. It should be benchmarked with latency percentiles. This is the software half of your HFT story. itch_fpga/ is the hardware half.

1Why this project matters
  • It's the #1 most common systems-design question at HFT/quant firms: "Design an order book. What data structures? What's the complexity of add/cancel/execute? How do you make it fast?"
  • It forces you to learn the things those firms test: cache behaviour, memory allocation, branch prediction, data layout, latency measurement.
  • It's AI-proof in interviews. The follow-ups are about measured trade-offs, which you only know if you built and profiled it.

Order types you should implement (in this order)

  1. Limit order: buy/sell up to qty at price P or better. The unfilled remainder rests.
  2. Market order: take whatever is available at any price. Never rests.
  3. Cancel: remove a resting order by id.
  4. Modify / replace: change price or qty. Priority rule (standard at most exchanges): reducing qty keeps time priority. Increasing qty or changing price loses it (treated as cancel + new).
  5. Time-in-force: GTC (rests until cancelled), IOC (fill what you can now, cancel the rest), FOK (fill entirely now or do nothing, so you need a liquidity check first).
  6. Stretch: post-only (reject if it would take), iceberg (displayed vs hidden qty), stop / stop-limit (trigger on last trade price).

Matching rules

  • Price-time priority (FIFO): better price first. At the same price, earlier order first. NASDAQ and most equities use this. Implement this.
  • Pro-rata: at a price level, fills are split proportional to size (some futures markets). Good interview talking point.
  • A trade happens at the resting (maker) order's price, not the aggressor's.
  • An incoming order sweeps levels: matches the best opposite level, then the next, until it's filled or the price no longer crosses.

3Data structures (the heart of the interview)

Operations & target complexity

Operation Target
Add order at existing level O(1)
Add order at new level O(log L) tree, or O(1) array
Cancel / delete by order id O(1)
Execute against best level O(1) per fill
Get best bid/ask O(1)
Get depth at price O(1)

Canonical design

Order        { id, side, price, qty, timestamp, prev*, next*, level* }   // intrusive list node
PriceLevel   { price, total_qty, count, head*, tail* }                   // FIFO queue of orders
Side (bids)  : price -> PriceLevel   (sorted; best = max)
Side (asks)  : price -> PriceLevel   (sorted; best = min)
OrderIndex   : order_id -> Order*    (hash map) — this gives O(1) cancel
  • Intrusive doubly linked list per level: the prev/next pointers live inside the Order, so unlinking on cancel is O(1) and allocates nothing.
  • Hash map id → Order*: O(1) lookup for cancel/execute. std::unordered_map is slow (node-based, one allocation per insert). Use an open-addressing map (linear probing, e.g. ankerl::unordered_dense, absl::flat_hash_map), or a plain vector indexed by id if ids are dense.

Price-level container: the big trade-off

Option Pros Cons
std::map<Price, Level> (red-black tree) Simple, handles any price Node allocation, pointer chasing, cache misses, O(log L)
Dense array indexed by tick (levels[price - base]) + cached best index O(1) everything, contiguous Needs bounded price range. Finding the next best after a level empties = scan (use a bitmap + ctz/clz to jump)
Sorted vector of levels, best at the back Most activity is near the top, so insert/erase near the back is cheap. Great cache locality. O(L) worst case insert
Hybrid: array window around the mid + map for far-away prices Best of both More code

Real-world insight (David Gross, Optiver, CppCon 2024): a typical stock book has ~1000 levels per side, but almost all activity is within a few levels of the top. So a sorted vector with best-at-the-end, searched linearly from the top, beats a tree in practice. Benchmark map vs vector vs array yourself. That benchmark table is your resume line.

Memory

  • Object pool / free list for Orders: preallocate N orders in a vector, hand out indices, recycle on delete. Zero malloc on the hot path.
  • Prefer indices (uint32) over pointers: smaller nodes, and the pool can be relocated.
  • Struct layout: put hot fields together, keep Order ≤ 64 B (one x86 cache line), avoid bool padding waste. Check with sizeof and static_assert.
  • Prices as integers (ticks, or ITCH's 4-implied-decimal uint32). Never use floating point for prices. Interviewers ask this.

Measuring latency correctly

  • Use std::chrono::steady_clock, or rdtsc (x86) / cntvct_el0 (ARM) for cycle counts. Measure per operation, record into a histogram, report p50/p90/p99/p99.9/max.
  • Warm up first (caches, branch predictors, page faults). Pin to a core on Linux.
  • Beware the compiler optimizing your benchmark away (benchmark::DoNotOptimize).
  • Throughput (msgs/sec over a whole file replay) and latency per op are separate metrics. Report both.

NASDAQ ITCH 5.0 Parser on FPGA

Goal: an RTL (SystemVerilog) block that takes a byte stream of NASDAQ ITCH 5.0 messages (from a file in simulation, later from UDP/MoldUDP64) and outputs decoded fields (type, order ref, side, shares, price, …) with deterministic latency of a few clock cycles. It's verified against your C++ parser from order_book/ as the golden model.

Why FPGAs in trading: a CPU path (NIC → kernel/bypass → parse → decide → send) costs ~1–5 µs. On an FPGA, the network PHY feeds logic directly, so parse+decide can take tens of ns with deterministic latency. Every serious HFT shop (Jump, Optiver, IMC, Citadel Securities, Tower, Graviton, Quadeye…) hires FPGA engineers, and "market data feed handler in RTL" is the canonical project.

1The protocol stack (what bytes arrive)
 Ethernet (14 B) │ IPv4 (20 B) │ UDP (8 B) │ MoldUDP64 header (20 B) │ [len(2) │ ITCH msg] [len(2) │ ITCH msg] ...
  • MoldUDP64 (NASDAQ's packet framing for multicast): Session (10 B ASCII) + Sequence Number (8 B, number of the first message in the packet) + Message Count (2 B). Then message blocks, each a 2-byte length + the message. Sequence numbers let you detect gaps (packet loss), which is an interview topic. Recovery goes through a request/retransmit server.
  • SoupBinTCP: the TCP equivalent (used for order entry/OUCH and some replay). Just know it exists.
  • The sample file from emi.nasdaq.com/ITCH/Nasdaq ITCH/ = the same [len(2) | msg] blocks back to back, with no UDP/Mold headers. Start with the file. It's the payload of the network stack.

ITCH 5.0 essentials

  • All integers big-endian. Alpha fields are ASCII, left-justified, space-padded.
  • Common header (11 bytes): Message Type (1, ASCII char) · Stock Locate (2) · Tracking Number (2) · Timestamp (6, ns since midnight).
  • Price(4) = uint32 with 4 implied decimals ($123.45 → 1234500). Price(8) has 8 decimals (MWCB only).

Always verify lengths and offsets against the official spec PDF. Don't trust this table (or an AI) blindly. Writing a tiny Python script that asserts sum(field sizes) == length for every message type is a good first task.

Key design insight: every message's length is known from its type byte, and it's given by the 2-byte length prefix anyway. So the parser never needs to scan for delimiters. That's why ITCH is FPGA-friendly.

3The core hardware problem: unaligned messages on a wide bus

A 10 GbE MAC typically gives you a 64-bit (8-byte) AXI-Stream at 156.25 MHz. ITCH messages are 12–50 bytes and start at any byte offset within an 8-byte beat. Example: a 36-byte Add Order followed by a 19-byte Delete:

beat 0: [len len A  loc loc trk trk ts ]
beat 1: [ts ts ts ts ts ref ref ref    ]
...
beat 4: [... price price | len len D loc]  <- message boundary mid-beat

Design approaches (pick one, explain why in your README):

  1. Byte-serial (1 byte/cycle). Trivial FSM with a byte counter. Easy, but 8× too slow for 10G at 156 MHz. Good v0.
  2. Shift-register / realignment buffer: accumulate bytes into a buffer wide enough for the longest message (50 B = 400 bits). When count ≥ msg_len, emit the whole message in parallel and shift out the consumed bytes. Needs a barrel shifter (muxes = LUTs = timing pressure).
  3. Per-type field extraction in parallel: once a full message is aligned, every field sits at a fixed offset for that type, so extraction is just wires + a mux on type. Output a wide struct: {type, locate, ts, ref, side, shares, price, new_ref, ...} with valid.
  4. Multiple messages per beat (stretch): two short messages can end and start in the same 8-byte beat. Handling >1 message/cycle is the "advanced" version and a great interview story.

Metrics: latency (cycles from last byte of message in → decoded valid out), throughput (bytes/cycle sustained), Fmax, LUT/FF usage.

5Verification strategy (this is what makes it credible)
  1. Golden model: your C++ (or Python) ITCH parser from order_book/ produces the expected decoded stream (CSV/JSON).
  2. cocotb testbench: reads the same file, drives bytes into the DUT with random tvalid gaps and random tready backpressure, captures outputs, and diffs them against the golden model. Run on millions of messages.
  3. Directed tests: each message type at every byte alignment (0–7), back-to-back short messages, max-length messages, packet boundaries.
  4. Assertions (SVA): valid held until ready, data stable while stalled, no output without input.
  5. Stretch: formal verification with SymbiYosys (ZipCPU's tutorials) to prove handshake properties.
  6. Report: "verified on N million messages from the NASDAQ sample day with randomized backpressure, zero mismatches."

1Chess rules that bite programmers

You know how pieces move. These are the edge cases that break move generators:

  • Castling (O-O / O-O-O): king and rook haven't moved (track 4 castling-rights flags), the squares between are empty, the king is not in check, doesn't pass through an attacked square, and doesn't land on one. The rook may pass through an attacked square (queenside b1/b8).
  • En passant: only immediately after an enemy pawn's double push. Track the en-passant target square. Nasty edge case: the en-passant capture can expose your king along the rank (both pawns vanish from the same rank). Test position for this in §3.
  • Promotion: to Q, R, B or N (underpromotion matters, e.g. knight promotion with check). Promotion with capture.
  • Legality: a move is illegal if it leaves your own king in check. This includes moving a pinned piece and the king walking into an attacked square, including a square "behind" itself along a slider's line.
  • Game end: checkmate, stalemate (no legal moves, not in check = draw), 50-move rule (halfmove clock, reset on pawn move/capture), threefold repetition (needs position hashing), insufficient material.

FEN (Forsyth–Edwards Notation): learn to read and write it

rnbqkbnr/pppppppp/8/8/4P3/8/PPPP1PPP/RNBQKBNR b KQkq e3 0 1 = piece placement (rank 8 → 1) · side to move · castling rights · en-passant square · halfmove clock · fullmove number. Your first engine function is load_fen / to_fen. All tests are FEN positions.

Notation: squares a1..h8. In code, index 0..63 with a1 = 0, h1 = 7, a8 = 56, h8 = 63 (the "little-endian rank-file" mapping most engines use).

Bitboard toolkit

  • Set ops: occupied = white | black, empty = ~occupied, us & them, etc.
  • Shifts: north = << 8, south = >> 8, east = << 1 masked with ~FILE_A (to avoid wrap-around), west = >> 1 & ~FILE_H.
  • Pawn pushes for all pawns at once: single = (pawns << 8) & empty, double = ((single & RANK_3) << 8) & empty.
  • Iterate pieces: while (bb) { sq = ctz(bb); bb &= bb - 1; } (__builtin_ctzll / std::countr_zero, which pops the lowest set bit).
  • popcount for counting (material, mobility).
  • Leapers (knight, king, pawn attacks): precomputed lookup tables KNIGHT_ATTACKS[64].
  • Sliders (bishop, rook, queen) depend on blockers:
    • Simple: loop ray by ray until you hit a piece ("classical approach" with ray tables + ctz/clz of blockers).
    • Fast: Magic bitboards. attacks = TABLE[sq][((occupied & mask[sq]) * MAGIC[sq]) >> shift[sq]]. A perfect-hash multiplication trick. Use known magic numbers (find your own with a random search later). On x86, PEXT (BMI2) does the same without magics. Your M2 has no PEXT, so use magics.

Move encoding

16-bit move: from (6 bits) | to (6 bits) | flags (4 bits: quiet, double push, castle K/Q, capture, en-passant, 4 promotions × capture/non-capture). Compact, fast to copy.

Make / unmake

  • make_move updates the bitboards, a mailbox piece_on[64] (keep both, since mailbox answers "what's on e4?" fast), castling rights, the ep square, clocks and the Zobrist hash. unmake_move restores. Or use copy-make (copy the whole ~200-byte state per ply), which is simpler, less bug-prone, and fast enough.
3Move generation and PERFT (the hardest 50%)

Pseudo-legal generation (ignore self-check) + a legality check after making the move ("is my king attacked?") is the simplest correct approach. Fully legal generation (compute pins and check masks up front) is faster. Do pseudo-legal first.

is_square_attacked(sq, by_color): the "super-piece" trick. From sq, generate knight attacks and see if they hit enemy knights, bishop attacks for enemy bishops/queens, rook attacks for rooks/queens, pawn attacks, king attacks.

4Search

Minimax → Negamax

  • Game tree: positions are nodes, moves are edges. Minimax: max player picks the max child, min player picks the min.
  • Negamax: score(pos) = max over moves of −score(child). One function for both sides. Eval is always from the side-to-move's perspective.
  • Branching factor in chess ≈ 35. Depth d costs 35^d nodes, so depth 6 ≈ 1.8 billion. Too many.

Alpha-beta pruning

  • Keep a window [α, β]: α = the best score we're guaranteed, β = the best the opponent allows. If a move scores ≥ β, the opponent would never let us get here, so cut off (fail-high).
  • With perfect move ordering, nodes ≈ 35^(d/2). You search twice as deep for the same cost. So move ordering is everything.
int negamax(pos, depth, alpha, beta):
    if depth == 0: return quiescence(pos, alpha, beta)
    for move in ordered_moves(pos):
        make(move)
        score = -negamax(pos, depth-1, -beta, -alpha)
        unmake(move)
        if score >= beta: return beta          // fail-hard cutoff
        alpha = max(alpha, score)
    if no legal moves: return in_check ? -MATE + ply : 0
    return alpha

Essential additions, in the order to add them (measure Elo after each, see §7)

  1. Quiescence search: at depth 0, keep searching captures only (plus promotions) until the position is quiet. "Stand pat" = static eval as a lower bound. Fixes the horizon effect (e.g. QxP looks great at depth 0 because the recapture is past the horizon). The single biggest strength gain.
  2. Move ordering: TT/hash move first → captures by MVV-LVA (Most Valuable Victim – Least Valuable Attacker: PxQ before QxP) or SEE (static exchange evaluation) → killer moves (quiet moves that caused cutoffs at the same ply) → history heuristic (quiet moves that caused cutoffs anywhere, weighted by depth²).
  3. Iterative deepening: search depth 1, 2, 3… until time runs out. It sounds wasteful but is faster overall because each iteration seeds move ordering (PV move, TT) for the next. It also gives you a move at any time → time management.
  4. Zobrist hashing: random 64-bit number per (piece, square), side to move, castling right and ep file. Position hash = XOR of the present ones. Updated incrementally in make/unmake (XOR in/out). Used for the TT and repetition detection.
  5. Transposition table (TT): a hash table keyed by Zobrist that stores {hash, depth, score, bound type, best move}. Bound type: EXACT (α < score < β), LOWER (fail-high, score ≥ β), UPPER (fail-low, score ≤ α). Lookup can cut off immediately or give the best move for ordering. Replacement scheme: depth-preferred + always-replace bucket. Mate scores need ply adjustment when stored/loaded.
  6. Principal Variation Search (PVS): search the first move with the full window, the rest with a null window (α, α+1) to just prove they're worse. Re-search if one surprises.
  7. Null-move pruning: "if I pass and I'm still ≥ β at reduced depth (R = 2–3), this position is so good I can cut." Don't use it in check or in pawn endgames (zugzwang).
  8. Late Move Reductions (LMR): moves late in the ordering are probably bad, so search them at reduced depth and re-search at full depth only if they beat α. Huge depth gain.
  9. Aspiration windows: at the root, search a narrow window around the last iteration's score. Re-search wider on failure.
  10. Later: check extensions, futility pruning, reverse futility (static null move), late move pruning, SEE pruning in qsearch, singular extensions. One at a time, each tested.

Repetition & 50-move detection in search: keep a stack of hashes. Treat the first repetition inside the search as a draw.

Time management

Simple: time_for_move = remaining/30 + increment/2. Stop iterative deepening when the next iteration likely won't finish. Check the clock every ~2048 nodes.

5Evaluation

Classical (hand-crafted, "HCE")

  • Material: P=100, N=320, B=330, R=500, Q=900 (centipawns).
  • Piece-square tables (PST): bonus/penalty per piece per square (knights in the centre good, on the rim bad, etc.).
  • Tapered eval: separate middlegame and endgame tables, blended by a game phase derived from remaining non-pawn material. The king hides in the middlegame and centralizes in the endgame.
  • PeSTO tables: published tuned midgame/endgame PSTs (CPW "PeSTO's Evaluation Function"). Material + PeSTO tapered PST alone ≈ a surprisingly strong engine (~2000+ with decent search).
  • More terms: mobility, pawn structure (doubled/isolated/passed pawns), bishop pair, rooks on open files, king safety (pawn shield, attackers near king).
  • Texel tuning: fit all eval weights by minimizing the MSE between sigmoid(eval) and actual game results over millions of positions. This is logistic regression / gradient descent, so it's your ML skillset.

NNUE (Efficiently Updatable Neural Network): modern eval, your sweet spot

  • Input: sparse one-hot features. Simplest form is 768 inputs = 2 colours × 6 pieces × 64 squares (Stockfish uses king-relative "HalfKA"-style features).
  • Architecture (simple, effective): 768 → 256 (accumulator, per perspective) → concat 512 → 1, clipped ReLU / SCReLU activation.
  • The trick: the first layer is huge but inputs change by only 2–4 features per move, so you incrementally update the accumulator: add/subtract weight columns on make/unmake instead of a full matmul. That's what makes the "EU" in NNUE.
  • Quantized int16/int8 inference with SIMD. Same skills as your neural accelerator project.
  • Training data: generate positions by self-play with your own engine (eval targets = search scores + game results), then train in PyTorch (or bullet, the Rust NNUE trainer most hobby engines use). A first net typically gains hundreds of Elo over HCE.

AlphaZero-style (MCTS + policy/value net): what your README dreams of

  • MCTS with PUCT selection: pick the child maximizing Q(s,a) + c·P(s,a)·√N(s)/(1+N(s,a)). Expand a leaf → the neural net gives policy P (move priors) and value v (expected outcome) → back up v. No alpha-beta and no handcrafted eval.
  • Training loop: self-play with MCTS → (position, MCTS visit distribution, game result) → train the net (cross-entropy on policy + MSE on value) → repeat.
  • Reality check: AlphaZero used thousands of TPUs. Leela Chess Zero took years of distributed community compute. On an M2 in a month, pure self-play from zero won't get strong.
  • Feasible version: supervised pretraining on Lichess games / Stockfish-labelled positions (a small ResNet or transformer, policy + value heads), then MCTS on top. It can reach a level that beats casual humans (≈ you!), and it's a fantastic ML project. Treat it as phase 2 / next semester, after the alpha-beta engine works.
  • Interview gold: why did NNUE + alpha-beta (Stockfish) end up beating the pure AlphaZero approach in CPU-limited settings? (Search depth × a cheap, accurate eval beats few nodes × an expensive eval when hardware is a CPU.)

Vector Database

Goal: a small but real vector database in C++ (or Rust): brute-force + HNSW + IVF-PQ indexes, a SIMD distance kernel, metadata filtering, persistence (WAL + snapshots / mmap), and a tiny HTTP/gRPC or Python API. It's benchmarked on SIFT1M / GloVe with recall-vs-QPS curves against FAISS / hnswlib.

Why it fits you: you've built LLMs and a RAG system (Vaani Board). This is the infrastructure underneath RAG. It reads well for ML-infra, backend and systems roles, and it's a natural system-design topic in AI-era interviews ("design semantic search for 1B documents").

1Foundations

Embeddings

  • An encoder maps text/images to vectors in ℝᵈ (d = 384, 768, 1024, 1536, 3072…) so that semantic similarity ≈ geometric closeness. Examples: sentence-transformers, OpenAI/Cohere/Voyage embeddings, CLIP for images.
  • Matryoshka embeddings: the first k dims are themselves a usable embedding, so you can truncate to trade accuracy for memory.
  • A vector DB stores (id, vector, metadata) and answers: given query q, return the k ids with the smallest distance.

Distance metrics

Metric Formula Notes
L2 (Euclidean) ‖x − q‖² Skip the sqrt for ranking
Inner product (IP) −x·q "MIPS". Not a true metric (no triangle inequality).
Cosine 1 − x·q/(‖x‖‖q‖) Normalize at insert → cosine == IP. Do this.
Hamming popcount(x XOR q) For binary-quantized vectors
Identity worth knowing: ‖x−q‖² = ‖x‖² + ‖q‖² − 2x·q. So batched L2 search = a matrix multiply (GEMM) + norms, which is how FAISS does brute force on GPUs.

Exact kNN (brute force, "Flat" index)

  • O(N·d) per query. With SIMD (NEON on your M2, AVX2/AVX-512 on x86) and a top-k heap (max-heap of size k), 1M × 128-d is ~tens of ms per query on one core.
  • Always build Flat first. It's your ground truth for recall.

The curse of dimensionality

  • In high d, distances concentrate (nearest and farthest neighbours become nearly equidistant), and space-partitioning trees (KD-tree, ball tree) degrade to brute force beyond ~20 dims.
  • So we use approximate NN (ANN): trade a bit of recall for orders-of-magnitude speed.

Metrics for ANN

  • Recall@k = |ANN top-k ∩ exact top-k| / k. QPS (queries/sec), latency p50/p99, build time, memory per vector, update/delete support.
  • The standard visualization is a recall-vs-QPS Pareto curve while sweeping a search parameter (efSearch, nprobe). This plot is your project's money shot.
2ANN index families

2.1 Hashing: LSH (know it, don't build it)

Random hyperplanes (SimHash) map similar vectors to the same bucket with high probability. Simple and theoretically clean, but it needs many tables for good recall. Mostly obsolete for dense embeddings and mostly appears as an interview question.

2.2 Clustering: IVF (Inverted File index)

  1. Train k-means on a sample to get nlist centroids (e.g. √N to 4√N).
  2. Each vector goes into the list ("posting list") of its nearest centroid.
  3. Query: find the nprobe nearest centroids, then scan only those lists. - Knobs: nlist (more = smaller lists, but more centroid comparisons), nprobe (more = higher recall, slower). - Failure mode: a query near a cluster boundary has true neighbours in an unprobed list, which is why nprobe > 1.

2.3 Quantization: compressing vectors

  • Scalar quantization (SQ8): float32 → int8 per dimension (min/max per dim). 4× smaller, small recall loss. Same idea as LLM int8 quantization, which you know.
  • Binary quantization: sign bit per dim → 32× smaller, Hamming distance via popcount. Use it for a fast first pass, then rerank with full vectors.
  • Product Quantization (PQ) (read this paper):
    • Split d dims into m subspaces (e.g. 128-d → m=16 × 8-d).
    • Run k-means in each subspace with 256 centroids → each sub-vector becomes a 1-byte code. A 128-d float vector (512 B) → 16 bytes.
    • ADC (asymmetric distance computation): for a query, precompute a table T[m][256] of distances from each query sub-vector to every sub-centroid. Distance to any database vector = m table lookups + adds. That's the trick that makes PQ fast.
    • IVF-PQ: IVF for coarse partitioning + PQ-encode the residual (vector − centroid). The workhorse of billion-scale search.
    • OPQ: learn a rotation first so subspaces are balanced. Know it exists.
    • Modern twist: fast-scan PQ with 4-bit codes and SIMD shuffle lookups (FAISS PQFastScan, Google ScaNN's anisotropic quantization).

2.4 Graphs: HNSW (the main thing to build)

  • Navigable small world (NSW): each vector is a node connected to ~M near neighbours. Search = greedy best-first walk from an entry point toward the query, keeping a candidate priority queue of size ef.
  • Hierarchical NSW: like a skip list over graphs. Each node gets a random max level l = floor(−ln(U) · mL) with mL = 1/ln(M). Upper layers are sparse "highways", layer 0 has everything.
  • Search: start at the top-layer entry point, greedy-descend with ef=1 to layer 1, then at layer 0 run the beam search with ef = efSearch, and return the top k.
  • Insert: pick the level, search down to find efConstruction candidates per layer, connect to M of them using the neighbour-selection heuristic (keep a candidate only if it's closer to the new node than to any already-selected neighbour, which spreads edges in diverse directions), add reverse edges, and prune neighbours exceeding M_max (layer 0 uses 2M).
  • Knobs: M (graph degree, 16–64), efConstruction (100–500, build quality), efSearch (query-time recall/speed dial).
  • Deletes are hard: use tombstones + skip at search time + periodic rebuild, or repair the neighbourhoods.
  • Pros: best recall/QPS in RAM. Cons: memory-hungry (vectors + edges ≈ (d·4 + M·2·4) B per vector), slow-ish build, random access patterns (bad for disk).

2.5 Disk-based graphs: DiskANN / Vamana (know it)

Single-layer graph built with α-pruning (α > 1 keeps longer edges), PQ codes in RAM for navigation, full vectors + adjacency on SSD, and a few SSD reads per hop. Billion-scale on one machine. Know the idea for system-design questions.

4Performance engineering (where you'll learn the most)
  • SIMD distance kernels: write L2/IP with NEON intrinsics (vfmaq_f32) on your M2, and compare against the auto-vectorized scalar loop. Look at the assembly (godbolt.org).
  • Memory layout: store vectors in one contiguous aligned array (SoA), not vector<vector<float>>. Store HNSW layer-0 adjacency in a flat fixed-size array per node (hnswlib's trick: vector + neighbours in one block, so one cache miss fetches both).
  • Prefetching (__builtin_prefetch) neighbours' vectors before computing distances during traversal.
  • Visited set: a reusable vector<uint16_t> with a generation counter instead of clearing a bitset per query.
  • Batching + multithreading for build and for batched queries.
  • Your LLaMA MFU work transfers directly: flat search is memory-bandwidth-bound. Compute the roofline. Bytes/query = N·d·4.

2Why accelerators exist: the numbers
  • DNN compute is dominated by matrix multiplies / convolutions = huge numbers of multiply-accumulates (MACs). Example: a 1024×1024 GEMM = 1.07 G MACs.
  • Energy is in data movement, not math. Approximate energy (45 nm, Horowitz ISSCC 2014): 8-bit add ~0.03 pJ, 32-bit float mult ~3.7 pJ, 32-bit SRAM read (small) ~5 pJ, DRAM read ~640 pJ. A DRAM access costs ~100–1000× a MAC. → Maximize reuse of each fetched value on-chip. Every accelerator design decision follows from this.
  • CPUs spend most energy on instruction fetch/decode/control. GPUs amortize that with SIMT. Accelerators remove it with fixed dataflow + huge MAC arrays + software-managed scratchpads (no caches).

Roofline model (know it cold)

  • Arithmetic intensity (AI) = FLOPs / bytes moved from memory.
  • Attainable perf = min(peak compute, AI × memory bandwidth). Below the "ridge point" you're memory-bound, above it compute-bound.
  • GEMM (n×n): FLOPs 2n³, bytes ~3n²·b, so AI ∝ n → compute-bound for big n. GEMV (batch-1 LLM decoding): AI ≈ 1–2 → memory-bound. That's why LLM inference is bandwidth-bound and why KV-cache/quantization matter. You know this from MFU work. Now you get the hardware reason.
3Number formats & quantization
  • Fixed point Qm.n: an integer with an implied binary point. Multiply Qa.b × Qc.d → Q(a+c).(b+d), then shift and round back. Saturate instead of wrapping on overflow.
  • int8 quantization (affine): real = scale · (q − zero_point). Per-tensor vs per-channel scales. Symmetric (zp = 0, simpler hardware) vs asymmetric.
  • int8 × int8 → int16 product. Summing K of them needs int32 accumulators (log2(K) extra bits of headroom).
  • Requantization: int32 accumulator → int8 output via (acc · M) >> shift where M is a fixed-point multiplier approximating s_in·s_w/s_out (Jacob et al. 2018). Implement this exactly, or your hardware won't match PyTorch.
  • Post-training quantization (PTQ) vs quantization-aware training (QAT). Newer formats to know: bf16, fp8 (E4M3/E5M2), int4, MX formats (microscaling, shared exponents per block).
  • Bit-exact verification: write the quantized inference in NumPy with integer ops. That's your golden model. RTL must match it bit for bit.

Systolic array (WS, how the TPU's MXU works)

  • A 2-D grid of Processing Elements (PEs). Each PE = a register holding a weight + a multiplier + an adder + registers to pass data to its neighbours. Only nearest-neighbour wires, so it scales to high clock rates. That's the whole point (H.T. Kung, 1978–82).
  • Preload weights W[k][n] into the PE grid. Activation rows enter from the left, skewed in time (row i delayed by i cycles) so the right values meet. Each PE computes psum_out = psum_in + a · w, passes a right and psum_out down. Results exit the bottom, de-skewed.
  • Timing: for an N×N array streaming M rows, latency ≈ M + 2N cycles. Throughput = N² MACs/cycle once full. Utilization drops for small M or when the matrix doesn't divide by N (the M2 ffn_dim lesson exactly).
  • Tiling: big matmuls are split into N×N weight tiles. The controller loops over tiles, accumulating partial results in an accumulator buffer. Double-buffer the weights (load the next tile while computing the current one) to hide load latency.
  • Conv → GEMM via im2col (unfold patches into columns), or do the conv natively with line buffers (option 2).

Memory hierarchy of an accelerator

DRAM → (DMA) → global buffer / scratchpad SRAM (FPGA BRAM) → PE-local registers. Software-managed (explicit loads), not caches. Double buffering / ping-pong buffers overlap transfer with compute. Bandwidth to the array: N activations + N psums per cycle, so BRAM width and partitioning matter.

Other efficiency tricks (know for interviews)

  • Sparsity: skip zero weights/activations. Structured 2:4 sparsity (NVIDIA Ampere) vs unstructured (needs index metadata, irregular).
  • Winograd / FFT convolution: fewer multiplies for 3×3 convs.
  • Operator fusion: keep intermediates on-chip (matmul → bias → ReLU → requant in one pass).
  • Non-linear functions in hardware: LUT + linear interpolation, piecewise-linear approximations, online softmax (running max + running sum, the FlashAttention trick, which maps nicely to streaming hardware).

2Big picture: the pipeline
source text
  → LEXER (tokens)
  → PARSER (AST)
  → SEMANTIC ANALYSIS (name resolution, scopes, types)  → annotated AST
  → IR GENERATION (three-address code / SSA, control-flow graph)
  → OPTIMIZATION PASSES (on IR)
  → INSTRUCTION SELECTION → REGISTER ALLOCATION → INSTRUCTION SCHEDULING
  → assembly → assembler → linker → executable

Front end = language-specific. Back end = machine-specific. IR decouples them (that's LLVM's whole idea: N languages × M targets → N + M work).

Compiler vs interpreter vs JIT: compile ahead of time to machine code / walk the AST or bytecode at runtime / compile hot code at runtime (V8, PyPy, LuaJIT, the JVM).

3Lexing (scanning)
  • Turn characters into tokens: KEYWORD(int), IDENT(x), INT_LIT(42), PLUS, LPAREN, …. Drop whitespace and comments, track line/column for error messages.
  • Theory: tokens are regular languages → regular expressions → NFA (Thompson's construction) → DFA (subset construction) → minimize. Tools like flex automate this. Hand-written lexers are just a loop with a switch on the current char: maximal munch (>= beats > then =), keyword lookup after scanning an identifier.
  • Interview: "Why can't regex parse nested parentheses?" (Regular languages can't count. You need a context-free grammar / pushdown automaton.)
4Parsing
  • Context-free grammars (CFG) in BNF/EBNF. Terminals, nonterminals, productions, derivations, parse trees vs AST (the AST drops the syntax noise).
  • Ambiguity: 1 - 2 - 3 and 1 + 2 * 3 → fix with precedence & associativity layers in the grammar.
  • Top-down (LL): recursive descent: one function per nonterminal. Needs no left recursion (rewrite expr → expr + term into a loop). LL(1) = decide with 1 lookahead token, using FIRST/FOLLOW sets.
  • Precedence climbing / Pratt parsing: the elegant way to parse expressions. Each token has a binding power, and a loop handles infix operators. Learn this. It's 50 lines and handles all of precedence, associativity, prefix and postfix.
  • Bottom-up (LR, LALR, SLR): shift-reduce with a parse table, used by yacc/bison. Know the concepts: shift/reduce and reduce/reduce conflicts, the dangling-else problem. You won't hand-write one.
  • Real compilers (GCC, Clang, Go, Rust's rustc) use hand-written recursive descent for better error messages.
  • Error recovery: panic mode, i.e. skip to a synchronizing token (;, }) and continue to report more errors.
5Semantic analysis
  • Symbol tables & scopes: a stack of hash maps. Lexical/static scoping, shadowing, name resolution, use-before-declare.
  • Type checking: compute each expression's type bottom-up and check the rules (can't add a pointer to a pointer). Implicit conversions (C's "usual arithmetic conversions"), lvalues vs rvalues.
  • Type inference (know it): Hindley–Milner / unification (ML, Haskell, Rust locally).
  • Output: an AST annotated with types and resolved symbols (or "variable #7, stack offset −24").
6Intermediate representation and optimization
  • Three-address code (TAC): t1 = a + b, one operation per instruction, explicit temporaries. Sandler's book calls its IR "TACKY".
  • Basic blocks (straight-line code, one entry, one exit) and the control-flow graph (CFG).
  • SSA (Static Single Assignment): every variable is assigned exactly once. φ (phi) functions merge values at join points. It makes most optimizations simple. Construct it via dominators / dominance frontiers (Cytron et al.). LLVM IR is SSA.
  • Dataflow analysis: a framework (lattice + transfer function + fixpoint iteration). Instances: liveness (backward), reaching definitions (forward), available expressions.
  • Classic optimizations (know what each does and give an example): | Pass | Example | |---|---| | Constant folding / propagation | x = 2*3; y = x+1 → y = 7 | | Dead code elimination | remove unused results, unreachable blocks | | Copy propagation | y = x; z = y+1 → z = x+1 | | Common subexpression elimination | compute a*b once | | Loop-invariant code motion | hoist n*4 out of the loop | | Strength reduction | i*4 in a loop → add 4 each iteration | | Inlining | replace a call with the body (enables everything else) | | Loop unrolling / vectorization | fewer branches, SIMD | | Tail-call optimization | recursion → loop |
7Back end
  • Instruction selection: map IR ops to machine instructions (tree pattern matching, or a simple 1:1 template expansion in a teaching compiler).
  • Register allocation: finite registers. Values that don't fit are spilled to the stack.
    • Graph coloring (Chaitin/Briggs): build an interference graph (variables live at the same time can't share a register) → K-color it (NP-hard, so use heuristics) → spill when you can't. Plus coalescing to remove moves.
    • Linear scan: faster and simpler, used in JITs.
  • Calling conventions / ABI: which registers hold args and the return value (x86-64 SysV: rdi, rsi, rdx, rcx, r8, r9, return in rax. AArch64: x0–x7, return in x0), caller- vs callee-saved registers, stack frames (frame pointer, return address, locals, alignment to 16 bytes).
  • Then assembler (text → object file) and linker (resolve symbols, relocations, link libc). Know ELF/Mach-O basics: sections .text, .data, .bss, symbol table.
  • Runtime topics for a dynamic language (option A): stack VM vs register VM, garbage collection (mark-sweep, copying, generational, reference counting + cycles), closures and upvalues, dynamic dispatch, NaN-boxing.
8ML compiler extras (option D)
  • Computational graph IR: nodes = tensor ops (matmul, add, relu, softmax), edges = tensors with shapes/dtypes.
  • Passes: shape inference, constant folding, operator fusion (matmul + bias + relu → one kernel, which saves memory round trips; the #1 win, see Horace He's "brrr" post), layout transformation (NCHW ↔ NHWC), quantization.
  • Loop-level IR: an op becomes a loop nest, then you tile for cache/SRAM, reorder, vectorize and parallelize. Halide's idea is separating the algorithm from the schedule, and TVM adopted it.
  • Polyhedral model (know the name): loop nests as integer polyhedra for legal reordering.
  • MLIR: multi-level IR with dialects (linalg, affine, scf, gpu…) progressively lowered. Triton = Python-level block programming → MLIR → PTX.
  • Lowering to your accelerator: tile a matmul to the systolic array size (e.g. 8×8), schedule weight loads/activation streams, and emit an instruction stream. That's what Google's XLA does for TPUs, in miniature.
